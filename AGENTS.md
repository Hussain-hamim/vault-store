# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

Desktop testing: keep `npm run dev` running, then use `npm run desktop:dev` (not a long-lived `npm run desktop` from before server edits). Unpackaged Electron loads the Vite UI and watches `server/` so ledger/API changes reload the DB worker without signing the user out (sessions are stored in SQLite). Desktop uses its own SQLite under Electron userData (not the browser demo DB).

## Store workflow decisions
- Inventory opens a colored card-style product list (category accent borders, stock badges) with a sticky search/header while the rows scroll; each card shows brand/model/SKU plus full saved specs (CPU/RAM/Storage/etc. by category), quantity, unit cost and selling price.
- Products can store a barcode on add/edit; New Sale/Purchase has a barcode scan field that looks up the product and adds it to the bill (Enter or Add). Catalog search also matches barcode.
- Customers use a teal/sky card list (rose when they owe); suppliers use a warmer clay/olive card list. Sticky search/header while contacts scroll; status chips show Owes you / Settled / Credit.
- Page content, dashboard, and sales workspace sit in a ~1280px centered column; inventory, customers, expenses/document history, daily book, and capital use a tighter ~960px column so side SVG décor stays visible. Sale history and expenses use colored card lists (status accents) like inventory/customers.
- Empty workspace margins show soft animated computer-store SVG decor (CSS motion). Capital uses Record investment modal; Where the money sits and Monthly capital sit side by side with color-coded amounts.
- Inventory, customers, suppliers, sale/purchase/expense history load 10 rows first; Load more appends the next 10. Tightened list screens use compact page headers and shorter cards.
- UI is PC-responsive across common laptop/desktop widths and Windows display scaling (about 1024–ultrawide CSS pixels): fluid page gutters, stacking list/trade/capital layouts under ~1280px, shorter chrome under ~820px height, and side SVG décor fades/hides when margins are tight.
- New products support unit cost and opening stock in the same form; unit cost and selling price sit side by side. Minimum price and shelf location are not collected on the product form for now.
- Stock is bought from Dubai in AED and sold in Afghanistan in AFN. Product and purchase forms record unit cost in the purchase currency plus the AFN conversion rate; optional per-unit cargo rent is added into the AFN landed unit cost for inventory/FIFO. Supplier quote stays separate from cargo on the line; invoice total and payables include cargo.
- Purchases keep cost batches (source currency + rate + AFN). Quantity-based stock uses FIFO. Individually tracked computers, mobiles and tablets still receive optional serials on purchase; New Sale uses quantity only (no device picker) and the server auto-assigns available devices FIFO. Cost/profit follow those assigned devices’ batches; returns still select exact returnable devices on that invoice.
- Product company/brand is chosen from a picker (Apple, Dell, Samsung, and similar; Other for a custom name).
- When category is Accessories, the form also asks for accessory type (keyboard, plush, hard disk, headphones, and similar; Other for a custom type).
- Product photos match category, company and exact model aliases using a bundled offline catalog of real product imagery; accessory type also participates in matching. Never show a different company's product. If the exact model is unavailable, clearly label a same-company/category photo as a reference or show a neutral icon. Add/edit product and new resale intake preview the match and accept an exact JPG/PNG/WebP upload. Reuse saved uploads for the same company/model; keep images offline in SQLite backups as separate, deduplicated BLOBs, with short image references in product rows and historical invoice snapshots. Photo sources/licenses live in Settings → About and `docs/product-photos.md`.
- Purchase invoices contain multiple product lines. Computers/laptops, phones and tablets use individual devices with optional serial/IMEI; accessories and storage remain quantity-based. Each individual device has a generated internal code and the cost of its actual receipt batch.
- New Purchase can create a product that is not yet in inventory (New product), then receive it on the same bill with AED cost and the invoice exchange rate.
- Purchases use a full-page bill editor with purchase-history view/edit/hard-delete (owner/manager). Editing reverses unsold received batches and reposts; blocked if any of that purchase stock was sold, or if returns/payments are linked.
- New Sale is a full-page bill editor, with a separate invoice-history section providing view, edit, hard-delete and download actions.
- New Sale and New Purchase use the same two-column board: left = party/date (sale also has Type name | Existing beside the name) + product catalog (cards stack cleanly, ~3+ visible then scroll); right = bill lines, compact totals/paid, Print-after-save checkbox, Cancel and post. No note field on these boards.
- Blank amount paid means unpaid (0), not full payment. Sale defaults to typing a customer name (saved to Customers); unpaid balances track on that customer. Existing walk-in remains cash-only. Payment due is not collected on sale/purchase boards.
- Print bill after save (default off) opens the invoice and print setup chooser when checked; the user then chooses the layout and confirms printing. Invoice view/print/download shows brand, model, SKU and full saved specs (CPU/RAM/Storage/etc. by category). Settings → Store holds bill design: business name, logo, phone, email, address, and optional footer used on print/download.
- UI languages: English (LTR), Pashto (`ps`, RTL), Dari (`prs`, RTL). Use proper Afghan shop/accounting terms (not literal calques). Language lives in store settings + localStorage; profile menu has a quick switcher. Layout stays the same; only labels and direction flip. Vazirmatn for Arabic-script locales; money amounts stay LTR-isolated. All screens, modals, and reports use `src/i18n` catalogs (`en`/`ps`/`prs`); report tabs and dashboard periods use stable IDs, not English labels. Product names, brands, SKUs, and server error text stay as entered/returned. Amount/qty fields use `NumericInput` (Western digits, LTR) so a Pashto/Dari OS keyboard still enters 0–9; Eastern digits are normalized on input/paste.
- Adding a customer or supplier uses opening balance (what they owe you / what you owe them) instead of credit limit; owner-only when the amount is greater than zero.
- Customer and supplier detail panels offer Edit and Delete (people permission). Delete is blocked while outstanding balance is not zero, with a clear message; soft-delete keeps invoice history. Walk-in cannot be edited or deleted.
- Customer/supplier ledgers show opening balances and payments newest-first with running outstanding, red/green amounts, and pagination; list Outstanding reflects that balance.
- Invoice mutations must update stock and ledgers atomically and enforce access rights and closed periods.
- Capital screen tracks owner capital and net worth month by month; owners invest or withdraw external cash there (updates cash + equity, not profit). Reports also include a Capital & net worth tab.

- Invoice/report Print and Download open the shared print chooser: four layouts, six color themes, A4/A5/Letter/A3 and invoice receipt widths (80/58 mm), orientation, margins and logo/spec/footer controls. Remember choices separately for invoices and reports on this computer. Preview, print and download use one standalone document with RTL support. Loaded-list and ledger-page printouts state their scope.

- Reports use top tabs with one dedicated report view at a time. Every report uses an understandable list with colored amounts, report-specific summary figures, explicit date/scope, and Print / Save PDF / Export CSV. Screen, print and CSV share the same report definition; exports include all report rows, not just the visible ten.
- Reorder & stock alerts includes every active product at or below its reorder level, zero stock first. Suggested order targets twice the reorder level (minimum target 1); this is a stock target, not demand forecasting. Costs are estimates using the latest stock-batch cost (saved AFN unit cost when no batch exists), with zero-cost items flagged. Reorder pages/export enforce a consistent audit revision and offer refresh if store data changes.

- Reports starts directly with a compact single row of horizontally scrollable report tabs; do not repeat a Reports eyebrow/title block. Zero stock is a separate printable/PDF/CSV report of active products with exactly zero units.
- Expenses use persistent, user-created expense accounts (Rent, Utilities, Food, Other and custom names). Expense entry selects an account; Expenses → Expense accounts shows period and lifetime spending. Existing expense categories migrate without changing postings. The expense history list shows description (note) instead of document reference, and the toolbar shows this month’s expense total (respecting the account filter) inline with the filters.
- Customer resale uses an agreed owner amount per unit (confirmed by the user). Receive customer-owned stock at zero shop inventory value, sell through the normal bill/FIFO workflow, and accrue the owner's agreed share on sale. Profit is sale revenue less the agreed share and other costs. Owner payouts/recoveries settle a separate owner-proceeds ledger and do not affect profit again.
- Sale returns restore original batches, reverse original cost/owner proceeds, and reduce profit. After an owner was paid, returned goods can leave a recoverable owner advance. Show owner advances as assets and owner dues as liabilities without offsetting different owners. Settled resale invoices cannot be edited/deleted; use sale returns. Unsold customer stock can be handed back through Customer resale without profit/cash effects.

## Purchase currencies and return workflow
- Purchases and product opening costs support saved selectable currencies with offline country flag artwork, plus Add currency wherever a currency picker appears. Custom currency code/name/flag is store-wide and persisted in SQLite. Store settings manages the same list.
- Each purchase saves its currency, supplier unit costs, and explicit AFN-per-unit exchange rate. AFN rate is 1. Changing currency clears old foreign quotes and rate to avoid silently relabeling costs. AFN ledgers and FIFO valuation remain the accounting base; preserve legacy AED invoices and batch data.
- Sale, purchase and return print-after-save checkboxes always start unchecked. Saving without an explicit checked option never opens the print chooser. Returns have a dedicated scrollable form, reason/date/quantities, and retain atomic stock and ledger reversals.

- Purchase currency UI stays compact inside the existing two-column bill board: supplier/date on one row, currency/rate side by side on the next. Use small 16×12 flags and a compact Add currency control; avoid repeated flags on line inputs. Bill cards give product identity a full row and quantity/cost/AF cost/discount one clear row.
- New purchase amount paid is entered in the selected invoice currency and converted to AF with that invoice’s rate. Show the live AF payment and record the exact original currency amount; invoice view/print/PDF show both. Preserve AF-only legacy payments without inventing a foreign amount, and keep all ledger postings in AFN.

- Sale/purchase catalog barcode scanning and product search share one compact row, each taking half the available width, with aligned control heights. Stack only on very narrow mobile widths. Preserve barcode Enter/Add behavior and catalog filtering.

- Sale bill cards use a full-width product identity row, then quantity/unit price/discount aligned in a separate three-column row; avoid squeezing product titles and price labels beside each other.
- Supplier balance payments support a saved payment currency and explicit current AF conversion rate. Show a live AF preview, save original amount/currency/rate, and show both amounts in supplier ledger and its printout. Allocations, cash, balances and running totals remain AFN; reject overpayments and conversion mismatches atomically.

- Keep the sidebar compact: Capital, Backups, and Help & Shortcuts live only inside Settings, alongside the existing About/Support sections. Remove the sidebar backup promo card. Existing shortcuts and dashboard links to these sections must open the corresponding Settings section, with Settings highlighted; retain capital/backup permissions and actions.

- Customer remaining-balance receipts share the supplier settlement currency workflow: default AFN at rate 1, allow any saved/custom currency with an explicit AF conversion rate, save original amount/currency/rate, and show both amounts in customer ledger, ledger printout and receipt. Keep receivable allocations, cash and running balances in AFN and reject mismatches/overpayments atomically.

- New Sale payment currency defaults to AFN at rate 1. Allow any saved/custom payment currency with live AF conversion; changing payment currency clears the payment/rate without changing AF product prices. Persist exact source amount/currency/rate and show both amounts in invoice view/print/PDF. Sale totals, receivables, cash and profit remain AFN; keep legacy AF-only edits intact.

- Sale returns allow refund currency selection, default AFN at rate 1, with original currency amount and AF conversion on return invoice/print/PDF. Reduce outstanding invoice debt first; only the remaining cash refund can be converted and paid. Validate exact converted refund against freshly calculated AF cash due; explain rounding mismatches and allow AFN for exact settlement. Preserve stock/FIFO/owner-ledger reversals and prevent duplicate refunds.

- Purchase returns accept supplier refunds in any saved currency, default AFN/rate 1. Reduce unpaid supplier debt first and convert only the cash receivable; preserve exact source refund amount/rate on invoice/print/PDF. Use the actual unsold purchase batches for return previews (including discounted cost rounding). Keep original purchase line currency separate from refund currency so supplier quotes are never relabeled.

## Desktop activation
- Fresh packaged Mac/Windows installs require online, single-PC activation before local owner setup. Signed Ed25519 receipts permit permanent offline use; usernames, passwords and shop data never go to licensing cloud. Worker/D1 configuration and administrator guide live in licensing/; never package signing private keys or admin tokens.
- Existing initialized SQLite stores receive a protected, device-bound legacy exemption at first upgrade. A pre-existing required-activation marker prevents later DB restore from granting exemption. Licensing stays outside SQLite/backups and is enforced in Electron main for commands, restore, print and backup modes. Browser/development stays unlicensed; never add a production environment-variable bypass.
- Package shared/ alongside server/ and zod in asarUnpack: the real Node database worker resolves ../shared/currencies.mjs from the unpacked directory. Every database worker must signal readiness, retain startup errors for later requests and time out failed initialization. Platform packaging runs the isolated native smoke test against the actual packaged executable/server; development-only smoke tests do not catch missing packaged imports.
- Owner recovery keeps normal login offline. Cloudflare stores only owner name/username/store name linked to a protected per-installation signing identity; never upload passwords or password hashes. Support verifies ownership and uses administrator Terminal commands to issue 30-minute one-time codes. New activations enroll automatically; older activated/legacy stores use a support-issued enrollment code. Identity keys stay outside shop backups. Reset authorizations bind the device, owner, request and random request commitment; local reset is atomic and invalidates sessions without altering store data or activation.

- Recovery UI shows only one-time recovery code and new-password fields; never show an enrollment-code field or button. New activations register automatically; older installations are approved by support in Terminal and finish registration automatically when checking recovery status.

- A successful owner password recovery creates a fresh local session and opens the store automatically. Revoke older sessions; do not send the owner back to manual sign-in after resetting.

- Local username/password login allows unlimited retries without a timed lockout; incorrect passwords still fail. Cloud activation and recovery service rate limits remain separate.

- Recovery now signs in using the one-time code alone; changing the password afterward is optional in Settings. Show the shop and username clearly and distinguish used, expired and wrong-store codes. Login prefills the local owner username and offers Show password. Keep the prior reset API compatible with older clients.

- Manually uploaded or previously saved custom product photos persist when category, brand, model or accessory type changes. Only choosing a replacement upload or explicitly using the automatic-photo action may replace them. Product edits that omit image fields preserve the existing photo.

- Remember previously used desktop shops and accounts on this computer. Closing the app retains the selected account session; explicit sign-out revokes that account session but preserves its chooser entry. Switching shops keeps SQLite, activation, recovery identity and protected sessions isolated per profile. Launch the last explicitly selected shop by default; never redirect scheduled backups to another shop.

- Hide the remembered-user picker when only one user is remembered. Hide the shop picker when only one shop is available, and hide the profile-menu switch action when neither has alternatives.

- Sign-in offers Remove for saved shops when multiple exist. Removal forgets the chooser entry persistently without deleting its SQLite, activation, backups or recovery identity. Removing the current shop switches to a remaining shop.

- The saved-shop selector stays available during owner recovery. Switching shops from recovery opens recovery for the chosen installation, even if that shop has a remembered session; references and codes must always belong to that chosen installation.

- Signed-in profile menus switch directly to another saved shop/account. Reuse its valid saved session without showing sign-in first; require credentials only when that destination has no valid session. Keep an explicit recovery-origin shop switch in recovery.

- Product details opened from global search or inventory show a prominent current-stock summary on the right of the product header. Use Details and Stock movement history tabs; show remaining stock after each movement, anchored to freshly loaded current stock even when only the latest 100 movements are shown.

## Individual device inventory
- New Computers (laptops/desktops), Mobiles and Tablets default to serialized device tracking. Manufacturer serial/IMEI is optional; supplied serials are unique without case sensitivity. Internal device codes are always generated. Accessories/Storage stay quantity FIFO; explicit `serialized:false` remains supported only for legacy API/import compatibility, with no opt-out on the normal product UI.
- Upgrade existing eligible remaining stock once, transactionally, into available device records using its original batch costs, without new stock or journal postings. Older invoices retain their original quantity history. Their returns create tracked devices at original cost; do not invent manufacturer serials. Legacy sales without device identities require return/new sale instead of edit after conversion.
- Purchase/opening-stock device details collect optional serial, condition, battery health, cosmetic notes and included accessories. Product details show identity/specs and stock movement only (no per-device picker or device list). Posted invoices retain immutable device snapshots. Device costs stay tied to batches, never mutable catalog prices.
- Purchase bills can repeat a device model on separate lines for different costs. New Sale merges by product and posts a quantity; the server auto-picks available units FIFO (explicit unit_ids still allowed for API/returns). Sale/purchase returns require exact returnable devices on that invoice. API posting checks status, product, original invoice and date atomically; duplicate/retried sales or returns cannot consume or refund a device twice.
- Unsold purchase edits preserve device IDs/codes. Existing device movement history blocks purchase rewrites that could invalidate it. Reacquiring a serialled device after supplier/owner hand-back reuses its physical identity with the new receipt cost. Returns and customer-resale owner proceeds use the selected units; unsold owner hand-back selects exact devices.
- Device lists page 50 rows and render inside bounded scrollers; receiving details expand on demand and show 10 rows initially. At most 1,000 individually tracked units per receipt line/opening entry. SQLite backups include device details and immutable line links. Invoice preview/print/PDF retain device identities even when optional specifications are hidden.
