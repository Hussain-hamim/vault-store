# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

Desktop testing: keep `npm run dev` running, then use `npm run desktop:dev` (not a long-lived `npm run desktop` from before server edits). Unpackaged Electron loads the Vite UI and watches `server/` so ledger/API changes reload the DB worker without signing the user out (sessions are stored in SQLite). Desktop uses its own SQLite under Electron userData (not the browser demo DB).

## Store workflow decisions
- Inventory opens a colored card-style product list (category accent borders, stock badges) with a sticky search/header while the rows scroll; each card shows brand/model/SKU plus full saved specs (CPU/RAM/Storage/etc. by category), quantity, unit cost (with purchase exchange rate when saved), and selling price. Toolbar filters use themed dropdown selects (no separate filter labels); Print, Save PDF, Export and Add Product share one toolbar row (no separate page-header action row). Sale/purchase/expense history and customers/suppliers put their primary New/Add action on the same Print/Export toolbar row. Opening a modal focuses the first text field (product name on Add Product); list screens autofocus search.
- Products can store a barcode on add/edit; New Sale/Purchase has a barcode scan field that looks up the product and adds it to the bill immediately (scanner burst, Enter, or Add). Rescanning a product already on the bill increases its quantity (capped by stock on sales). Catalog search and global search also match barcode (exact or partial, case-insensitive). On the Dashboard, a USB barcode scan with no field focused opens that product’s details.
- Enter advances focus like Tab inside forms, modals, and sale/purchase boards (barcode scan fields, listboxes, and buttons keep their own Enter behavior). In Add Product, Enter/Tab walk Product info → Specifications → Pricing, then land on the primary Save action; other modals likewise continue from the last field to their action buttons.
- Customers use a teal/sky card list (rose when they owe); suppliers use a warmer clay/olive card list. Sticky search/header while contacts scroll; status chips show Owes you / Settled / Credit.
- Page content, dashboard, and sales workspace sit in a ~1280px centered column; inventory, customers, expenses/document history, daily book, and capital use a tighter ~960px column so side SVG décor stays visible. Sale history and expenses use colored card lists (status accents) like inventory/customers.
- Empty workspace margins show soft animated computer-store SVG decor (CSS motion). Capital uses Record investment modal; Where the money sits and Monthly capital sit side by side with color-coded amounts.
- Inventory, customers, suppliers, sale/purchase/expense history load 10 rows first; Load more appends the next 10. Tightened list screens use compact page headers and shorter cards.
- UI is PC-responsive across common laptop/desktop widths and Windows display scaling (about 1024–ultrawide CSS pixels): fluid page gutters, stacking list/trade/capital layouts under ~1280px, shorter chrome under ~820px height, and side SVG décor fades/hides when margins are tight.
- New products support unit cost and opening stock in the same form; unit cost and selling price sit side by side. Editing a product also shows stock on hand; saving posts an inventory adjustment for the difference (serialized reductions still use Product Detail → Adjust to pick devices). Minimum price and shelf location are not collected on the product form for now.
- New products start with an empty barcode; Generate fills a store code (`RTM` + digits) that can be regenerated or replaced with a factory barcode. Generate and Print live on the product form and product details (not as a top Inventory toolbar action). Label jobs print a scannable QR (not Code 128 bars) on dedicated 29×18 mm thermal stock; copy count is chosen in the print preview/setup dialog (default on-hand qty), one sticky label per page/copy. Condition and warranty are not collected on the product form; device-detail expanders are not shown on add/edit (devices are still created for serialized stock).
- Stock is bought from Dubai in AED and sold in Afghanistan in AFN. Product and purchase forms record unit cost in the purchase currency plus the AFN conversion rate; optional per-unit cargo rent is always entered in AFN and added into the AFN landed unit cost for inventory/FIFO. Supplier quote stays separate from cargo on the line; invoice total and payables include cargo.
- Purchases keep cost batches (source currency + rate + AFN). Quantity-based stock uses FIFO. Individually tracked computers, mobiles, tablets and cameras still receive optional serials on purchase; New Sale uses quantity only (no device picker) and the server auto-assigns available devices FIFO. Cost/profit follow those assigned devices’ batches; returns still select exact returnable devices on that invoice.
- Product company/brand is chosen from a picker (Apple, Dell, Samsung, Canon, Nikon and similar; Other for a custom name).
- Product category includes Computers, Mobiles, Tablets, Cameras, Storage, Accessories, plus Other for a custom store category (persisted when used). Computers collect Generation with the other PC specs. Cameras collect camera type (DSLR, Mirrorless, Action, CCTV, DVR/NVR, Security kit, Webcam, Lens, and similar). Photo cameras use sensor/resolution/lens/mount/ISO/video fields; CCTV/security types switch to night vision, IR range, power (PoE/12V), cable, channels, audio, housing, IP rating, viewing angle and included kit items (cable/adapter/mount). Product entry omits the barcode hint line and stays compact enough to avoid scrolling at normal laptop heights.
- Add Customer and Record Expense modals include Save & New and Previous (session history only); Previous loads the prior saved record for edit/update, not a duplicate create.
- When category is Accessories, the form also asks for accessory type (keyboard, plush, hard disk, headphones, and similar; Other for a custom type).
- Automatic product photos use the clean studio category/accessory illustrations (laptop, phone, tablet, storage, keyboard, etc.), not phone-style Wikimedia snapshots. Users who do not upload a PC photo get that studio look. Custom JPG/PNG/WebP uploads and in-app camera capture still override and are reused for the same company/model; keep those images offline in the live SQLite as separate, deduplicated BLOBs, with short image references in product rows and historical invoice snapshots. Backup copies omit camera/file photo BLOBs and rewrite `photo:` refs to studio images so restore shows the bundled illustrations. Photo notes live in Settings → About and `docs/product-photos.md`.
- Purchase invoices contain multiple product lines. Computers/laptops, phones, tablets and cameras use individual devices with optional serial/IMEI; accessories and storage remain quantity-based. Each individual device has a generated internal code and the cost of its actual receipt batch.
- New Purchase can create a product that is not yet in inventory (New product), then receive it on the same bill with AED cost and the invoice exchange rate.
- Purchases use a full-page bill editor with purchase-history view/edit/hard-delete (owner/manager). Editing reverses unsold received batches and reposts; blocked if any of that purchase stock was sold, or if returns/payments are linked.
- New Sale is a full-page bill editor, with a separate invoice-history section providing view, edit, hard-delete and download actions.
- New Sale and New Purchase use the same two-column board: left = party/date (sale also has Type name | Existing beside the name) + product catalog (cards stack cleanly, ~3+ visible then scroll); right = bill lines, compact totals/paid, Print-after-save checkbox, Cancel and post. No note field on these boards. Existing customer (sale) and supplier (purchase) use a searchable contact field that opens a paginated list (10 at a time, Load more) instead of a plain dropdown. Purchase catalog cards show current on-hand stock for each product. Sale keeps the lime/olive board; purchase uses a warmer clay/amber board and tab accent so the two screens are easy to tell apart.
- Blank amount paid means unpaid (0), not full payment. Sale defaults to typing a customer name (saved to Customers); unpaid balances track on that customer. Existing walk-in remains cash-only. Payment due is not collected on sale/purchase boards.
- Print bill after save (default off) opens the invoice and print setup chooser when checked; the user then chooses the layout and confirms printing. Invoice view/print/download shows brand, model, SKU and full saved specs (CPU/RAM/Storage/etc. by category). Settings → Store bill design drives sale invoices only: English + Pashto store names centered between left/right logos, services, up to two owners (name/phone), bill note, customer signature line, and Pashto address at the bottom; purchase/returns/receipts keep the standard header. Legacy single logo migrates to the left logo. Bill design Save keeps typed values (remount only after fresh settings load). Store/language save failures must show an error. Windows production uses `signExecutable: false` so the TechMart icon is embedded in the exe (do not use `signAndEditExecutable: false`).
- UI languages: English (LTR), Pashto (`ps`, RTL), Dari (`prs`, RTL). Use proper Afghan shop/accounting terms (not literal calques). Language lives in Settings → Account (and Store when managing settings) plus localStorage; sign-out is on the same Account tab—no sidebar profile block. Layout stays the same; only labels and direction flip. Vazirmatn for Arabic-script locales; money amounts stay LTR-isolated. All screens, modals, and reports use `src/i18n` catalogs (`en`/`ps`/`prs`); report tabs and dashboard periods use stable IDs, not English labels. Product names, brands, SKUs, and server error text stay as entered/returned. Amount/qty fields use `NumericInput` (Western digits, LTR) so a Pashto/Dari OS keyboard still enters 0–9; phone, barcode and SKU fields also normalize Eastern digits to Western 0–9 on input/paste.
- No top search bar in the chrome; notifications live at the top of the sidebar (above quick actions). Global search remains available via Ctrl/Cmd+F / palette. Customers and suppliers toolbars include Print and Save PDF for the loaded contact list. Day book rows emphasize the party/contact name over the invoice reference.
- Adding a customer or supplier uses opening balance (what they owe you / what you owe them) instead of credit limit; owner-only when the amount is greater than zero.
- Customer and supplier list cards offer Edit and Delete (people permission); the side panel is ledger-only (no duplicate contact block). Delete is blocked while outstanding balance is not zero, with a clear message; soft-delete keeps invoice history. Walk-in cannot be edited or deleted. Customer receipts and supplier payments can be hard-deleted from the opened payment document (owner/manager + finance), which reverses allocations, cash and party ledger. Destructive deletes across the app use a simple Are you sure? confirm (Cancel / Delete)—never require typing an invoice number or DELETE.
- Customer/supplier ledgers show payments newest-first in fixed Date / Reference / Debit / Credit / Balance columns with bold red/green debit/credit/running amounts (no opening-balance button or ledger hint paragraphs on the ledger panel). Print / Save PDF remain available. Contact phones use a country-code picker (default Afghanistan +93) with per-country digit length checks; stored as `+{dial}{national}`. The closed picker shows only the dial code (`+93`), not the country name or Windows flag letters. WhatsApp sharing was removed from invoices, ledgers and reports.
- Invoice mutations must update stock and ledgers atomically and enforce access rights and closed periods.
- WhatsApp invoice/ledger actions have been removed. Use Print and Save PDF for document output.
- Capital screen tracks owner capital and net worth month by month; owners invest or withdraw external cash there (updates cash + equity, not profit). Reports also include a Capital & net worth tab.

- Invoice/report Print and Download open the shared print chooser: four layouts, six color themes, A4/A5/Letter/A3 and invoice receipt widths (80/58 mm), orientation, margins and logo/spec/footer controls. Remember choices separately for invoices and reports on this computer. Preview, print and download use one standalone document with RTL support. Loaded-list and ledger-page printouts state their scope.

- Reports use top tabs with one dedicated report view at a time. Every report uses an understandable list with colored amounts, report-specific summary figures, explicit date/scope, and Print / Save PDF / Export CSV. Screen, print and CSV share the same report definition; exports include all report rows, not just the visible ten. Performance tabs include Profit & loss, Daily, Invoice profit (per sale/return), Product profitability, Resale profit (customer-owned stock: revenue − owner share), and Cash & money (balances as of end date plus period cash by document type).
- Low stock report (Reports → Low stock) lists every active product at or below its reorder level, zero stock first, with Print / Save PDF / Export CSV. Suggested order targets twice the reorder level (minimum target 1); this is a stock target, not demand forecasting. Costs are estimates using the latest stock-batch cost (saved AFN unit cost when no batch exists), with zero-cost items flagged. Reorder pages/export enforce a consistent audit revision and offer refresh if store data changes. Dashboard Low stock and Restock “See all” open this report tab.
- Available stock report (Reports → Available stock) lists every active shop product with stock greater than zero (excludes consignment-only), with on-hand qty, reorder level and estimated stock value; Print / Save PDF / Export CSV use the same definition and full export paging as other stock alerts.
- Reports starts directly with a compact single row of horizontally scrollable report tabs; do not repeat a Reports eyebrow/title block. Do not show on-screen report formula/hint descriptions; keep date/scope filters on the same row as Print / Save PDF / Export CSV. Zero stock is a separate printable/PDF/CSV report of active products with exactly zero units.
- New sale invoice numbers use unpadded `SAL-{n}` (1, 2, 3…). Sale/purchase/expense history search matches document number (prefix or contains) as well as party name/phone. Invoice list customer/supplier names are shown in bold.
- Expenses use persistent, user-created expense accounts (Rent, Utilities, Food, Other and custom names). Expense entry selects an account; Expenses → Expense accounts shows period and lifetime spending. Existing expense categories migrate without changing postings. The expense history list shows description (note) instead of document reference, and the toolbar shows this month’s expense total (respecting the account filter) inline with the filters.
- Customer resale uses an agreed owner amount per unit (confirmed by the user). Receive customer-owned stock at zero shop inventory value, sell through the normal bill/FIFO workflow, and accrue the owner's agreed share on sale. Profit is sale revenue less the agreed share and other costs. Owner payouts/recoveries settle a separate owner-proceeds ledger and do not affect profit again.
- Sale returns restore original batches, reverse original cost/owner proceeds, and reduce profit. After an owner was paid, returned goods can leave a recoverable owner advance. Show owner advances as assets and owner dues as liabilities without offsetting different owners. Settled resale invoices cannot be edited/deleted; use sale returns. Unsold customer stock can be handed back through Customer resale without profit/cash effects.

## Desktop activation
- Fresh packaged Mac/Windows installs require online, single-PC activation before local owner setup. Signed Ed25519 receipts permit permanent offline use; usernames, passwords and shop data never go to licensing cloud. Worker/D1 configuration and administrator guide live in licensing/; never package signing private keys or admin tokens.
- Existing initialized SQLite stores receive a protected, device-bound legacy exemption at first upgrade. A pre-existing required-activation marker prevents later DB restore from granting exemption. Licensing stays outside SQLite/backups and is enforced in Electron main for commands, restore, print and backup modes. Browser/development stays unlicensed; never add a production environment-variable bypass.
- Package shared/ alongside server/ and zod in asarUnpack: the real Node database worker resolves ../shared/currencies.mjs from the unpacked directory. Every database worker must signal readiness, retain startup errors for later requests and time out failed initialization. Platform packaging runs the isolated native smoke test against the actual packaged executable/server; development-only smoke tests do not catch missing packaged imports.
- Owner recovery keeps normal login offline. Cloudflare stores only owner name/username/store name linked to a protected per-installation signing identity; never upload passwords or password hashes. Support verifies ownership and uses administrator Terminal commands to issue 30-minute one-time codes. New activations enroll automatically; older activated/legacy stores use a support-issued enrollment code. Identity keys stay outside shop backups. Reset authorizations bind the device, owner, request and random request commitment; local reset is atomic and invalidates sessions without altering store data or activation.

- Recovery UI shows only one-time recovery code and new-password fields; never show an enrollment-code field or button. New activations register automatically; older installations are approved by support in Terminal and finish registration automatically when checking recovery status.

- A successful owner password recovery creates a fresh local session and opens the store automatically. Revoke older sessions; do not send the owner back to manual sign-in after resetting.

- Local username/password login allows unlimited retries without a timed lockout; incorrect passwords still fail. Cloud activation and recovery service rate limits remain separate.

- Recovery now signs in using the one-time code alone; changing the password afterward is optional in Settings. Show the shop and username clearly and distinguish used, expired and wrong-store codes. Login prefills the local owner username and offers Show password. Keep the prior reset API compatible with older clients.

- Manually uploaded or previously saved custom product photos persist when category, brand, model or accessory type changes. Only choosing a replacement upload or explicitly using the automatic-photo action may replace them. Product edits that omit image fields preserve the existing photo.

- Remember previously used desktop shops and accounts on this computer. Closing the app retains the selected account session; explicit sign-out revokes that account session but preserves its chooser entry. Switching shops keeps SQLite, activation, recovery identity and protected sessions isolated per profile. Launch the last explicitly selected shop by default; never redirect scheduled backups to another shop.

- Hide the remembered-user picker when only one user is remembered. Hide the shop picker when only one shop is available, and hide the profile-menu switch action when neither has alternatives.

- Sign-in offers Remove for saved shops when multiple exist. Removal forgets the chooser entry persistently without deleting its SQLite, activation, backups or recovery identity. Removing the current shop switches to a remaining shop.

- The saved-shop selector stays available during owner recovery. Switching shops from recovery opens recovery for the chosen installation, even if that shop has a remembered session; references and codes must always belong to that chosen installation.

- Restoring a backup with a different owner adds a separate shop profile after confirmation instead of replacing the current shop. Each imported shop gets a fresh activation-required guard before its database is copied; never copy activation, recovery keys or remembered sessions between shops.
